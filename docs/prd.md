# Orbit — Predict Satellite Position 경진대회 및 머신러닝 과제 PRD

수정일: 2026-09-22

## 1. Project Overview

### 1.1 Project Definition

제공된 CSV로 Y_Position을 예측하는 두 방법을 각각 개발한다. 첫째는 학습 데이터에서 관찰한 원의 수식을 구현한 모델이고, 둘째는 그 수식을 입력이나 정답 변환에 사용하지 않고 데이터로 학습한 머신러닝 모델이다. 두 모델을 검증한 뒤 사용자가 Kaggle에 직접 제출할 수 있는 파일과 과제 자료를 준비한다. [S1][S2][S9]

### 1.2 Background

학습 데이터에는 Y_Position 정답이 있지만 시험 데이터에는 없다. 과제에서는 피처 선택을 반드시 적용하고, 개발 과정의 단계별 RMSE·소스코드·리더보드 캡처를 제출해야 한다. 대회 순위는 RMSE가 아닌 Huber 손실로 정해진다. [S1][S5]

기존 탐색에서 학습 데이터의 (X_Position, Y_Position) 점들은 중심 (630, 550), 반지름 420인 원 위에 부동소수점 오차 수준으로 놓였으며 위·아래는 Velocity × Altitude의 부호와 일치했다. 이는 강력한 후보 규칙이지만 학습 데이터에서 발견된 사실이다. 공개·비공개 시험 정답에 대한 성능 보증은 아니다. 따라서 수식에 의존하지 않는 머신러닝 모델도 독립된 개발 경로로 만든다. [S2][S9]

### 1.3 Target Environment

개발AI는 CSV 읽기, 학습, 검증, 두 제출 CSV 생성, 보고서 초안 작성을 수행한다. Kaggle 계정 접속, 실제 파일 업로드 및 리더보드 캡처는 사용자가 수행한다. [S8]

## 2. Goals & Success Definition

### 2.1 Project Goals

1. 대회 평가 점수를 가능한 한 0에 가깝게 낮추고 최종 1위를 목표로 한다. 순위는 보장하지 않는다.
2. 결정론적 수식 모델 A와 독립적인 머신러닝 모델 B를 모두 완성하고 같은 검증 자료에서 비교한다.
3. 모델 B에 과제 필수 조건인 피처 선택을 실제로 적용하고 선택 전후 성능을 기록한다.
4. 두 모델 각각의 시험 데이터 예측 CSV와 실행 가능한 소스코드를 준비한다.
5. 단계별 RMSE, Kaggle 점수, 피처 선택, 개발 과정을 이해하기 쉬운 보고서에 정리하고 사용자가 제공하는 리더보드 캡처를 첨부한다. [S1][S9]

### 2.2 Goal Completion State

개발AI는 검증된 두 제출 CSV, 소스코드, 비교 결과, 업로드 안내, 보고서 초안을 사용자에게 인계한다. 사용자가 각 파일을 Kaggle에 제출하고 실제 점수와 캡처를 전달하면 개발AI가 이를 반영해 보고서를 완성한다.

### 2.3 Overall Success Conditions

과제 요구사항이 충족되고 두 방법의 실제 검증 결과가 구분되어 기록된다. Kaggle 공개 점수와 최종 비공개 순위는 사용자 제출 이후에만 확인된 사실로 기재한다. 두 모델이 같은 학습 분포를 사용하므로 두 모델 개발만으로 숨겨진 데이터의 분포 변화 위험이 사라지는 것은 아니다.

## 4. Functional Requirements

### FR-01. 입력 데이터와 제출 양식 확인

**Purpose / Rationale:** 세 파일의 역할을 혼동하지 않고 재현 가능한 학습·예측을 하기 위함이다.

**Trigger:** 개발 시작 시.

**Input:** Train_DS..csv, Test_DS..csv, Sample_Submission_DS..csv.

**Processing / Business Rules:**

- 학습 파일은 636,363행, 시험 파일과 샘플 제출 파일은 각 63,000행으로 확인되었다. 실행 시 다시 검사한다. [S2][S3][S4]
- 입력 열은 Satellite_ID, X_Position, Velocity, Altitude, Fuel_Level, Signal_Strength, Battery_Temp, Solar_Exposure이다. 정답은 학습 파일에만 있는 Y_Position이다. 현재 파일에서 Satellite_ID는 정수형, 나머지는 숫자형으로 읽힌다. [S2][S3]
- Satellite_ID는 예측 변수로 자동 사용하지 않는다. 시험 행과 제출 행을 연결하는 ID로 유지한다.
- 학습·시험의 열 이름, 행 수, 중복 ID, 결측, 비숫자 값, 주요 열의 분포·범위를 확인한다. 특히 학습과 시험의 각 입력 열의 범위와 분위수를 비교하고 차이가 있으면 기록한다.
- 샘플 제출물의 Y_Position 값 63은 정답이 아닌 자리 채움 값이다. 제출 CSV는 ID와 행 순서를 샘플과 동일하게 맞춘다. [S4]

**Output / Expected State:** 학습·시험·제출 스키마와 입력 분포 요약.

**Acceptance Criteria:** 정답 열과 입력 열이 구분되고 제출 행 대응을 확인할 수 있다.

### FR-02. 공통 검증과 성능 기록

**Purpose / Rationale:** 두 모델과 피처 선택 전후를 같은 조건에서 비교하기 위함이다.

**Trigger:** 입력 검사가 끝난 뒤.

**Input:** 정답이 있는 학습 데이터.

**Processing / Business Rules:**

1. 원본 행 인덱스 0부터 N-1까지를 NumPy default_rng(42).permutation(N)으로 섞는다. 앞쪽 ceil(0.2 × N)개를 최종 비교 구간, 나머지를 개발 구간으로 정한다. 현재 파일에서는 비교 구간이 127,273행이다.
2. 모델 B의 피처 선택·모델 선택·하이퍼파라미터 조정은 개발 구간 내부의 고정된 3겹 교차검증에서 수행한다. 최종 비교 구간의 정답으로 피처나 하이퍼파라미터를 고르지 않는다.
3. 모든 단계에서 같은 최종 비교 구간에 대해 RMSE, 대회 방식의 Huber 점수, 최대 절대오차를 계산한다.
4. 최소한 개발 구간의 Y 평균을 예측하는 기준선, 수식 모델 A, 전체 원본 입력을 쓴 모델 B, 피처를 줄인 후보 중 가장 성능이 좋은 모델 B, 최종 선택 모델 B를 기록한다. 최종 모델이 전체 입력 모델과 같으면 같은 결과임을 명시한다.
5. X 범위별 구간과 위·아래 가지별 오차도 확인해 전체 평균이 일부 구간의 큰 오류를 가리지 않는지 살핀다.
6. 원 규칙은 이 PRD 작성 전에 학습 CSV 전체를 탐색해 발견되었다. 그러므로 모델 A의 내부 20% 점수를 완전히 독립적인 최초 발견 검증으로 설명하지 않는다. 모델 B 역시 같은 대회 데이터를 사용하므로 비공개 시험 성능을 보장한다고 표현하지 않는다. [S2]

**Output / Expected State:** 단계별 입력·모델·RMSE·Huber·최대 오차 및 구간별 성능 기록.

**Acceptance Criteria:** 동일한 분할과 지표로 두 모델이 비교되고 시드·분할 방법·검증 한계가 보고서에 적힌다.

### FR-03. 모델 A — 발견한 수식의 구현

**Purpose / Rationale:** 학습 데이터에서 관찰된 거의 정확한 관계를 별도의 예측 후보로 확인하기 위함이다.

**Trigger:** 공통 검증 구간 확정 후.

**Input:** X_Position, Velocity, Altitude, 개발 구간의 X_Position·Y_Position.

**Processing / Business Rules:**

1. 개발 구간의 (X_Position, Y_Position) 점에서 원 중심 (a, b)와 반지름 r을 추정한다. 원의 일반식 x² + y² + Dx + Ey + F = 0을 최소제곱으로 맞추고 a = -D/2, b = -E/2, r = sqrt(a² + b² - F)를 계산한다. 앞선 탐색에서 관찰된 값은 약 (630, 550, 420)이다. [S2]
2. q = r² - (X_Position - a)²를 계산한다. q ≥ 0이고 Velocity × Altitude > 0이면 b + sqrt(q), 곱이 음수이면 b - sqrt(q)를 예측한다.
3. q < 0 또는 Velocity × Altitude = 0이면 확인된 가지가 없으므로 Y = b를 대체값으로 쓰고 해당 행·사유·건수를 기록한다. 현재 제공된 학습·시험 파일에는 이 두 예외가 관찰되지 않았다. [S2][S3]
4. 모델 A에는 다른 관측 열, 모델 B의 예측값, Kaggle 공개 점수를 입력으로 넣지 않는다.
5. 공통 비교 구간에서 성능을 측정하고, 최종 제출 파일 생성 시에는 학습 데이터 전체에서 중심·반지름을 다시 추정한다.

**Output / Expected State:** 모델 A의 검증 기록과 시험 데이터 예측값.

**Acceptance Criteria:** 공식·매개변수·예외 건수가 기록되고 시험 데이터 전체에 유한한 예측값이 생성된다.

### FR-04. 모델 B — 수식에 의존하지 않는 머신러닝 학습

**Purpose / Rationale:** 원 공식이 숨겨진 시험 자료에서 예상대로 작동하지 않을 위험에 대비하고, 실제로 학습되는 별도 예측 모델을 확보하기 위함이다.

**Trigger:** 공통 검증 구간 확정 후. 모델 A의 예측값은 필요하지 않다.

**Input:** 학습 데이터의 Y_Position과 Satellite_ID를 제외한 일곱 원본 입력 열.

**Processing / Business Rules:**

1. Y_Position 자체를 학습 목표로 하는 비선형 표 데이터 회귀 모델을 학습한다. 약 51만 개발 행을 반복 학습해야 하므로 대규모 표 데이터에 적합한 효율적인 모델을 우선 검토한다. 예시는 조기 종료를 지원하는 GBDT 계열이다. 모델 종류와 라이브러리는 구현자가 선택하고 이유·설정·실행 시간을 기록한다.
2. 원본 숫자 열에 더해 절댓값·제곱·부호, 관측 열 사이의 쌍별 곱이나 부호 조합 같은 일반적인 피처 계산을 **후보로 검토**한다. 모든 파생 피처를 한꺼번에 생성하거나 반드시 유지할 필요는 없다. 특정한 Velocity × Altitude 조합만 정답을 알고 골라 추가하지 않는다. 후보 피처의 개수와 메모리 사용량을 확인한다.
3. 모델 B에는 원 중심 630·550, 반지름 420, 모델 A의 예측값, 원 공식의 오차·가지 정답, Y_Position으로부터 계산한 대체 목표를 입력하거나 하드코딩하지 않는다. 숫자 전처리의 기준값과 결측 대체값은 해당 학습 접힘에서만 추정한다.
4. 일곱 원본 입력 열을 모두 사용하는 모델을 먼저 학습·평가한다. 이어 FR-05의 머신러닝용 피처 선택 실험에서 원본 열을 줄인 후보들을 학습·비교한다. 최종 모델 B에는 교차검증에서 가장 낮은 Huber 점수를 얻은 입력 집합을 사용하며, 그 집합은 일곱 열 전체일 수도 있다. 선택된 원본 열에서만 파생 피처를 다시 계산해 제외된 열이 파생 피처를 통해 유입되지 않게 한다.
5. 개발 구간 내부 교차검증의 Huber 점수를 모델 B의 주된 선택 기준으로 삼고 RMSE도 함께 기록한다. 선택이 끝난 뒤 공통 최종 비교 구간에서는 한 번 평가한다.

**Output / Expected State:** 학습된 최종 모델 B, 전체 입력·축소 입력 후보·최종 선택 입력의 성능, 최종 모델의 시험 예측값.

**Acceptance Criteria:** 모델 B는 실제 학습된 예측기로서 모델 A와 독립된 코드를 가지며, 원 공식 없이 예측을 재현할 수 있다.

### FR-05. 모델 B의 필수 피처 선택

**Purpose / Rationale:** 과제 필수 요건을 모델 B의 학습 목적에 맞는 절차로 이행하기 위함이다.

**Trigger:** 모델 B의 전체 입력 기준 모델이 준비된 후.

**Input:** 개발 구간의 일곱 원본 입력 열, 학습 정답, 모델 B.

**Processing / Business Rules:**

1. 피처 중요도와 여러 부분집합의 반복 비교는 개발 구간에서 고정 시드 42로 추출한 최대 100,000행의 선별용 표본에 우선 적용한다. 이 표본 내부의 고정된 3겹 교차검증에서 원본 입력 열별 **그룹 단위 순열 중요도(Grouped Permutation Importance)**를 계산한다. 한 원본 열을 검증 접힘에서 섞을 때 그 열에서 만든 파생 피처도 함께 다시 계산하여 해당 원본 열의 전체 영향을 측정한다. 중요도는 섞기 전후 Huber 손실 차이의 접힘 평균이다. 최종 비교용 20%의 정답은 여기에 사용하지 않는다.
2. 중요도 순위의 상위 k개 원본 열을 선택하는 후보를 k = 1, 2, 3, 4, 5, 6, 7로 평가한다. k = 7은 전체 입력 기준이며 k ≤ 6은 실제로 열을 줄인 피처 선택 실험군이다. 각 후보에서는 선택된 원본 열에서만 파생 피처를 만들고 같은 종류의 모델과 같은 검증 절차를 사용한다.
3. 평균 교차검증 Huber 점수가 가장 낮은 k를 최종 모델 B의 입력 집합으로 정한다. 동점이면 원본 열이 더 적은 후보를 선택한다. k = 7이 최선이어도 최고 성능의 k ≤ 6 후보를 별도 실험군으로 남겨 선택 전후 점수를 보고한다. 점수가 나빠졌다면 그대로 적고 성능을 위해 최종 모델 B는 전체 열을 유지한다.
4. 모델 B의 선택 결과를 미리 X_Position·Velocity·Altitude로 고정하지 않는다. 모델 A용 수식에서 쓰인 세 열과 다를 수 있으며, 중요도·선택 열·제외 열·전체/축소/최종 성능을 모두 기록한다.
5. 선별용 표본에서 모델·피처 후보의 계산량을 확인한 뒤 최종으로 고른 구성만 개발 구간 전체에 학습하여 공통 비교 구간에서 평가한다. 최종 제출용 모델 B는 같은 구성으로 학습 데이터 전체에 다시 학습한다. 조기 종료·트리 복잡도 제한 등 모델에 맞는 자원 관리 방식을 사용하고, 실행 시간이 과도하거나 메모리가 부족하면 표본·후보 피처·모델 설정을 줄여 재평가하며 변경 내역을 기록한다.

**Output / Expected State:** 모델 B의 중요도 순위, 최고 축소 후보와 최종 입력 집합, 전체/축소/최종 성능 및 자원 사용 기록.

**Acceptance Criteria:** 원 공식의 상·하 부호 일치율이 아닌 모델 B의 검증 손실로 피처 선택 실험을 수행하고, 최소 한 열을 제외한 모델을 실제로 학습·평가한다. 최종 모델에서 열을 반드시 제외하도록 강제하지 않는다.

### FR-06. 두 제출 파일의 생성과 사용자 인계

**Purpose / Rationale:** 사용자가 Kaggle에서 두 모델의 실제 점수를 확인할 수 있게 하기 위함이다.

**Trigger:** 두 모델의 검증과 최종 학습이 완료된 후.

**Input:** Test_DS..csv, Sample_Submission_DS..csv, 모델 A와 모델 B.

**Processing / Business Rules:**

- 모델 A와 모델 B에 대해 각각 63,000행의 예측 CSV를 별도로 생성한다. 두 파일명은 어느 모델의 결과인지 구별할 수 있게 한다.
- 두 파일 모두 열은 Satellite_ID, Y_Position 순서로 두고 샘플 제출물의 ID·행 순서와 일치시킨다. 누락·비숫자·무한대 예측값이 있으면 사용자 인계 전에 해결한다. [S3][S4]
- 개발AI는 각 파일의 위치와 사용자가 Kaggle에서 따라 할 짧은 업로드 순서를 제공한다. 개발AI가 Kaggle에 직접 업로드하거나 실제 점수를 확인했다고 주장하지 않는다. [S8]
- 사용자가 두 파일을 직접 제출한 뒤 각 파일의 공개 점수와 리더보드 캡처를 전달한다. 개발AI는 받은 결과와 내부 검증 점수를 함께 해석한다.

**Output / Expected State:** 검증된 두 제출 CSV, 업로드 안내, 사용자 제출 후의 두 실제 공개 점수.

**Acceptance Criteria:** 개발AI 인계 단계에서는 두 유효한 CSV와 안내가 제공된다. 사용자 제출 후에만 실제 Kaggle 점수를 보고서에 기록한다.

### FR-07. 과제 보고서와 소스코드

**Purpose / Rationale:** 교수자가 방법·성능·피처 선택을 확인할 수 있게 하기 위함이다.

**Trigger:** 개발AI의 검증 완료 후 초안을 작성하고, 사용자 제출 결과를 받은 뒤 마무리한다.

**Input:** 두 모델의 코드와 검증 기록, 피처 선택 결과, 사용자가 전달한 Kaggle 점수·캡처.

**Processing / Business Rules:**

- 기준선, 모델 A, 전체 입력 모델 B, 최고 축소 후보 모델 B, 최종 선택 모델 B의 단계별 RMSE와 Huber 점수를 표로 요약한다. 같은 모델이 중복된 단계는 중복임을 표시한다.
- 모델 A가 학습 데이터 탐색에서 먼저 발견되었고 모델 B는 공식 없이 학습되었음을 구분해 설명한다. 피처 선택이 성능을 개선했는지 여부도 측정한 대로 쓴다.
- Kaggle 제출 전에는 공개 점수와 캡처를 미확인으로 표시한다. 사용자가 제공한 실제 자료만 최종 보고서에 반영한다.
- 실행 가능한 두 모델의 소스코드와 실행 절차를 첨부한다. [S1][S8]

**Output / Expected State:** 사용자 결과 전달 전 보고서 초안, 전달 후 과제 제출용 최종 보고서.

**Acceptance Criteria:** 개발 과정·단계별 RMSE·피처 선택·소스코드·리더보드 캡처가 포함된다. [S1]

## 5. Business / System Rules

### BR-01. 점수의 역할

RMSE = sqrt(mean((실제 Y - 예측 Y)²))이며 과제에 단계별로 보고한다. 대회 Huber 점수는 오차 절댓값이 5 이하일 때 0.5 × 오차², 초과일 때 5 × (오차 절댓값 - 2.5)를 행별로 적용해 평균낸 후 1,000을 곱한다. 대회 점수는 낮을수록 좋다. 두 지표를 혼용하지 않는다. [S1][S5]

### BR-02. 공개·비공개 평가의 구분

확인된 대회 페이지에서 공개 리더보드는 시험 데이터 약 37%, 최종 결과는 나머지 약 63%로 계산된다. 사용자가 언급한 67%는 현재 페이지의 비율과 다르므로 PRD에서는 63%로 표기한다. 공개 점수는 개별 행 정답을 공개하지 않으며 비공개 순위를 보장하지 않는다. [S6]

### BR-03. Kaggle 역할과 선택

사용자가 Kaggle 제출·캡처를 담당한다. 개발AI는 두 모델의 검증 결과와 사용자가 전달한 공개 점수를 함께 설명한다. 공개 점수만 반복 최적화하지 않으며, 두 제출 파일 중 최종 후보의 선택 이유를 기록한다. 어느 한 모델의 우위를 시험 정답 확인 전에 단정하지 않는다. [S8][S9]

## 6. State & Data Model

| 데이터        | 열 및 상태                                                                                                                        | 역할                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 학습 CSV      | Satellite_ID 정수형; X_Position, Velocity, Altitude, Fuel_Level, Signal_Strength, Battery_Temp, Solar_Exposure, Y_Position 숫자형 | 학습·검증의 원자료       |
| 시험 CSV      | 위 입력 열만 있고 Y_Position 없음                                                                                                 | 두 모델의 최종 예측 대상  |
| 샘플 제출 CSV | Satellite_ID, Y_Position                                                                                                          | 제출 열과 행 순서의 기준  |
| 모델 A        | 추정 중심·반지름과 부호 규칙                                                                                                     | 결정론적 예측 후보        |
| 모델 B        | 선택 원본 열, 일반 파생 피처 정의, 전처리 값, 학습된 모델                                                                         | 독립적 머신러닝 예측 후보 |
| 제출 결과     | 모델 식별자, 제출 파일, 사용자 전달 점수·캡처                                                                                    | 보고서와 최종 후보 비교   |

현재 제공된 학습·시험 CSV에는 결측이 관찰되지 않았다. 모델 B에서 새 결측이 발생하면 학습 접힘의 중앙값으로 대체하는 전처리를 해당 접힘 안에서 학습하고 시험 데이터에 동일하게 적용한다. 모델 A의 필수 입력이 누락·비숫자이면 근거 없는 예측을 만들어 제출하지 않고 해당 행을 확인한다. [S2][S3]

## 8. Error & Edge Cases

### EC-01. 모델 A의 제곱근 내부 음수 또는 부호 0

q < 0 또는 Velocity × Altitude = 0이면 중심 Y값 b를 대체값으로 내고 해당 ID·사유·건수를 기록한다. 현 데이터에는 두 예외 행이 없다. [S2][S3]

### EC-02. 입력 누락·형식 오류

모델 B는 학습 접힘에서 얻은 중앙값으로 숫자 결측을 대체한다. 모델 A 필수 입력의 누락·비숫자, 제출 파일의 행 수·ID 순서·비유한 예측값 오류는 인계 전에 확인하고 해결한다.

### EC-03. 두 모델의 검증 결과가 다르거나 시험 분포가 다름

어느 한 모델을 자동으로 정답이라 가정하지 않는다. 내부 구간별 오차, 학습/시험 입력 분포 차이, 사용자 전달 공개 점수를 함께 기록해 최종 후보를 판단한다. 시험 정답을 직접 확인했다고 주장하지 않는다.

### EC-04. 사용자 제출 결과가 아직 없음

두 CSV·소스코드·보고서 초안을 인계하고 Kaggle 점수·캡처는 미확인 상태로 둔다. 사용자가 실제 결과를 전달한 뒤 보고서의 해당 부분을 완성한다. [S8]

## 10. Non-Functional Requirements

- 고정 분할과 기록된 실행 환경으로 두 모델의 학습·검증·예측을 재현할 수 있어야 한다.
- 소스코드와 보고서는 초보 학부생이 단계와 결과를 따라갈 수 있게 설명한다.
- 관찰하지 않은 비공개 정답·점수·순위를 확정된 사실처럼 쓰지 않는다.
- 모델 B의 결측 대체 등 학습되는 전처리 값은 교차검증의 각 학습 접힘에서만 추정한다. 해당 검증 접힘의 정답은 중요도와 후보 성능 계산에 사용할 수 있지만, 최종 비교용 20%의 정답은 피처·설정 선택에 사용하지 않는다. 후보 비교는 먼저 선별용 표본에서 수행하고 최종 구성만 전체 개발 구간에 학습한다.

## 11. External Dependencies & Required Setup

Kaggle 대회 참가·업로드에는 사용자의 계정과 대회 접근 권한이 필요하다. 개발AI의 직접 로그인을 요구하지 않는다. 개발AI는 선택한 Python 버전, 필수 라이브러리와 실제 사용 버전을 소스코드와 함께 명시하고 재현 가능한 설치·실행 절차를 제공한다. PRD 단계에서 아직 선택되지 않은 라이브러리의 최소 버전을 임의로 고정하지 않는다. 비밀번호·토큰은 PRD나 보고서에 기록하지 않는다. [S5][S8]

## 12. Technical Constraints & Approved Technical Decisions

### 12.1 Technical Constraints

- 피처 선택은 모델 B에 실제로 적용하고 선택 전후 점수를 보고한다. [S1][S9]
- 단계별 RMSE와 실행 가능한 소스코드, 사용자 전달 리더보드 캡처를 과제에 포함한다. [S1]
- 두 모델의 제출물은 샘플 CSV의 열과 행 대응을 따른다. [S4]
- 모델 B는 모델 A의 공식·매개변수·예측값을 학습 입력으로 사용하지 않는다. [S9]

### 12.2 Approved Technical Decisions

- 모델 A는 관찰된 원 관계를 구현한다. 모델 B는 Y_Position을 직접 학습하는 별도 머신러닝 회귀 모델이다. [S2][S9]
- 두 모델은 같은 최종 비교 구간에서 RMSE와 Huber 점수를 측정한다.
- Kaggle 제출과 리더보드 캡처는 사용자가 수행한다. [S8]
- 배깅·스태킹은 과제의 선택 사항이며 필수 개발 절차로 채택하지 않는다. [S1]

### 12.3 Implementation Freedom

위에서 명시되지 않은 내부 구현 세부사항은 승인된 목표와 요구사항을 위배하지 않는 한 개발 담당자가 합리적으로 결정할 수 있다. 클래스명, 함수명, 내부 파일 구조, 구체적인 비선형 회귀 알고리즘과 라이브러리는 별도로 승인된 제약이 없는 한 강제하지 않는다.

## 13. Acceptance Criteria

### 13.1 Functional Acceptance

- 학습·시험·샘플 CSV의 스키마, 데이터 상태 및 입력 분포가 확인된다.
- 모델 A와 모델 B가 별도 코드 경로로 실행되고 동일한 비교 구간에서 평가된다.
- 모델 B가 원 공식 없이 학습·예측되며, 그룹 단위 순열 중요도와 최소 한 축소 입력 후보의 실제 학습·비교를 통해 피처 선택을 수행한다.
- 최종 모델 B의 입력 집합은 전체 7개 또는 축소 집합 중 교차검증 Huber 점수가 가장 낮은 쪽으로 결정된다.
- 기준선, 모델 A, 전체 입력 모델 B, 최고 축소 후보 모델 B, 최종 모델 B의 RMSE와 Huber 점수가 기록된다.
- 모델별 63,000행 제출 CSV가 두 개 생성되고 샘플 제출물과 열·ID·행 순서가 맞는다.
- 개발AI는 두 파일과 사용자 업로드 안내를 인계하며 Kaggle 제출 완료를 허위로 주장하지 않는다.

### 13.2 System Acceptance

개발AI의 인계물은 두 제출 CSV, 두 모델의 소스코드, 실행 환경·절차, 성능 비교, 보고서 초안이다. 사용자가 실제 Kaggle 점수와 캡처를 제공한 뒤 이를 반영한 보고서가 과제에 제출 가능한 최종 상태가 된다.

### 13.3 User Acceptance

사용자는 두 모델이 어떻게 다른지, 피처 선택이 모델 B에 어떻게 적용됐는지, 각 모델의 RMSE와 Kaggle 점수가 무엇인지 이해할 수 있다. 직접 두 CSV를 제출하고 실제 결과를 개발AI에게 전달할 수 있다.
